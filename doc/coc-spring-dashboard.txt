==============================================================================
INTRODUCTION                                     *coc-spring-dashboard-intro*

coc-spring-dashboard shows the Spring Boot apps of the workspace in tree
views:

- The apps, running or stopped. |coc-spring-dashboard-apps|
- The beans of each app. |coc-spring-dashboard-beans|
- The endpoint mappings of each app. |coc-spring-dashboard-mappings|
- The properties of each running app. |coc-spring-dashboard-properties|
- The memory of each running app as sparklines.
  |coc-spring-dashboard-memory|

It also puts signs on bean definitions and request mappings in Java buffers
|coc-spring-dashboard-signs| and connects remote apps
|coc-spring-dashboard-remote|.

Installation, requirements, setup and settings are in the README of the
extension.

coc-spring-dashboard defines no key mappings. You use it through
`:CocCommand`, the tree windows and their actions menu.

==============================================================================
QUICKSTART                                   *coc-spring-dashboard-quickstart*

Open the apps tree and start an app from it: >vim
    :CocCommand spring-boot-dashboard.list
<
The tree opens in a vertical split on the right. Pick an app and Run it, then
open its dashboard with the actions key of the tree (`<Tab>` by default).
|coc-spring-dashboard-actions| All commands are listed in
|coc-spring-dashboard-commands|.

==============================================================================
LIVE AND STATIC DATA                               *coc-spring-dashboard-live*

Static data comes from the source code: the beans and request mappings that
coc-springboot finds in the workspace. It is there as soon as the project is
indexed.

Live data comes from a running app: its beans, mappings, properties and
memory. An app shows live data once the Spring language server of
coc-springboot is connected to it. The README lists what the app needs.

The dashboard needs two servers: the Java server (coc-java) for the apps, Run,
Debug, Attach debugger and the launch settings, the Spring Boot server
(coc-springboot) for the live and static data, the remote apps and the
refresh. It checks locally whether their commands are registered and asks no
server for that; the Java server counts as up only once it has imported the
projects, which coc-java reports (its "ServiceReady"), since before that it
finds no apps. An action that needs a server which is not up says "Java server
starting" or "Spring Boot server not running" and does nothing else; Run does
not wait for the Spring Boot server. Work in the background waits for the
server instead of polling it: the live data of a started app is connected once
the Spring Boot server is up, by sending it the pid of the app (as for the
remote apps, so it does not depend on
`boot-java.live-information.all-local-java-processes`), and the beans and
mappings of the workspace are loaded once it is up and tried again while they
come back empty.

Icons of an app or of the group of an app in a tree:

  Icon   Meaning ~
  `●`      the app is running, the group shows live data
  `○`      the app is stopped, the group shows static data

The description after a group says which data it shows:

  Description      Meaning ~
  `live, all`        live data, every bean or mapping of the app
  `live, defined`    live data, only what is defined in the source
  `defined`          static data from the source

Refresh the live data of the connected apps by hand: >vim
    :CocCommand spring-boot-dashboard.livedata.refresh
<
The static data rescans the source by itself when you save and when the
index changes.

COMMANDS                                       *coc-spring-dashboard-commands*

Every command that `:CocCommand` lists, by what you do. The other commands of
the extension are actions of the trees and are described under
|coc-spring-dashboard-actions|.

SPRING APPS lists the Spring Boot apps whose source is in this workspace,
whether they run or not and whoever started them. A local app is one of them;
the `app.local` commands work on it. A remote app is one you connect to by its
address or from `boot-java.remote-apps`, with the `app.remote` commands; its
source may or may not be in this workspace.

Workspace ~
  `spring-boot-dashboard.list`                 open SPRING APPS, the Spring
                                               Boot apps of the workspace
  `spring-boot-dashboard.refresh`              look for them again

Local apps ~
  `spring-boot-dashboard.app.local.run`        start an app in a terminal and
                                               open its dashboard tab
  `spring-boot-dashboard.app.local.debug`      start an app under the debugger
                                               and open its dashboard tab
  `spring-boot-dashboard.app.local.settings`   edit how an app starts:
                                               profiles, port, logging, JVM
                                               options, args, environment
  `spring-boot-dashboard.app.local.attach`     attach the debugger to an app
                                               started with Run, without a
                                               restart
  `spring-boot-dashboard.app.local.dashboard`  switch to the dashboard tab of
                                               an app started with Run or
                                               Debug
  `spring-boot-dashboard.app.local.stop`       stop an app: SIGTERM, then
                                               SIGKILL after the grace period
  `spring-boot-dashboard.app.local.open`       open an app with live data in
                                               the browser

Remote apps ~
  `spring-boot-dashboard.app.remote.attach`    attach to an app by address:
                                               live data over JMX, the
                                               debugger over JDWP, and open
                                               its dashboard tab
                                               |coc-spring-dashboard-attach|
  `spring-boot-dashboard.app.remote.connect`   connect the live data of an
                                               entry of
                                               `boot-java.remote-apps`
                                               |coc-spring-dashboard-remote|
  `spring-boot-dashboard.app.remote.disconnect`
                                               disconnect the live data of a
                                               remote app the dashboard
                                               connected

Local and remote apps ~
  `spring-boot-dashboard.livedata.refresh`     reload the live data of every
                                               connected app

Without a tree line the app commands ask which app to use.

------------------------------------------------------------------------------
APPS                                               *coc-spring-dashboard-apps*

One line per Spring Boot app whose source is in this workspace, whoever
started it. The icon and description show its state:

  `○` stopped             not running
  `◐` starting            the JVM is being started
  `◐` waiting for debugger  Debug started the JVM, it waits for the debugger
  `●` running             running; `running :8080` shows the port when live
                        data is connected, also for apps started outside
  `◉` debugging           a debugger is attached
  `◎` attached            connected with Attach to a remote app;
                        `attached host:port` shows where it runs

An app you started yourself on this machine shows as running once its live
data is connected. An app you connected with Attach to a remote app shows as
attached, on the lines of the project you picked in the attach panel. You
cannot Run or Debug an attached app, so that it does not run twice, and Stop
and Attach debugger leave it alone; disconnect it to work on it locally again.
An app connected from `boot-java.remote-apps` shows as stopped, even when its
source is in this workspace. The live data of a remote app shows in the views
and in its dashboard tab.

The tooltip shows the main class. `spring-boot-dashboard.refresh` reloads the
list of apps.

Run, Debug and Stop are real. Run and Debug open the launch panel, one
quick pick per app with the action first and the settings below it: >
    Debug bootlab
    ▶ Debug with these settings
      Profiles       dev, local
      Server port    default
      Logging        INFO (debug report: off)
      JVM options    -Xmx512m
      Program args   none
      Environment    DB_URL=...
      Reset to settings
<
Picking a setting edits it and returns to the panel, the action launches and
`<Esc>` cancels. The panel edits the settings of the app,
`spring.dashboard.launch.defaults` joins them at launch (see below). Picking
the action remembers them per app (kept per workspace); until then they are
the entry of the app in `spring.dashboard.launch.settings`. "Reset to
settings" puts that entry back in the panel, picking the action then
remembers it; `<Esc>` keeps what was remembered before. Once settings are
remembered, a change to that entry takes effect only after "Reset to
settings" and the action.

  Profiles        a multi-select of the profiles found like upstream does:
                  the `application-<p>` and `bootstrap-<p>` files (properties,
                  yml, yaml) in the source folders of the project and their
                  `config` subfolders. Profiles typed before are offered
                  again, "Type another profile..." adds new ones. Passed as
                  `-Dspring.profiles.active=a,b`.
  Server port     "App default" passes nothing, "Random (0)", or a number;
                  passed as `-Dserver.port=N`. Spring config files are not
                  read for it.
  Logging         the root level (`-Dlogging.level.root`), per package levels
                  such as `com.example=DEBUG` (`-Dlogging.level.<pkg>`) and
                  the `--debug` auto-configuration report.
  JVM options     separated by spaces, quotes group: `-Xmx512m -Dfoo=bar`.
  Program args    separated by spaces, e.g. `--server.address=0.0.0.0`.
  Environment     `KEY=VALUE` pairs for the JVM.

`spring.dashboard.launch.prompt` says when the panel opens: `always` (default,
every Run and Debug), `first` (the first time per app, then the remembered
settings are used) or `never`. The "with profile" variants open the panel with
the profiles list already open (also with `never`); a profile given as
argument skips it. "Launch settings..." in the tree actions and
`spring-boot-dashboard.app.local.settings` open the panel without launching.

The app starts as a JVM named "Spring: <app>". The JMX port, host and
project name the live data needs are added per run, the rest of what it needs
is in the default `vmArgs` (see below). The classpath comes from the Java
language server and is passed in an argument file in the storage folder of
the extension. Each app gets a tab at the end of the tab line, its dashboard,
with the working directory set to the project (`:tcd`):
>
    +-----------+-----------+------------+----------+
    | BEANS     | MAPPINGS  | PROPERTIES | MEMORY   |   top,
    |           |           |            |          |   4 equal columns
    +-----------+-----------+------------+----------+
    | terminal: the JVM of this run, with the output |   bottom, 65% of
    |                                                |   the height
    +------------------------------------------------+
<
`spring.dashboard.layout.terminalHeight` sets the percent of the height the
terminal gets, from 10 to 90, 65 by default.

`spring.dashboard.layout.components` picks the panes, to free space: any of
"beans", "endpoints", "properties", "memory" and "terminal", all of them by
default. The panes keep the places above whatever the order of the list. A
view left out is not shown anywhere. With the terminal left out the JVM keeps
running in it without a window and the views fill the tab, as in the tab of a
remote app. An empty list, or one with only unknown names, is all of them.

The terminal has the output, colors and input. With
`spring.dashboard.layout.cleanup` set to "keep", running again reuses the tab:
the new terminal replaces the old one, the views stay. Run switches to the tab
and leaves the focus in the terminal. "Show app dashboard" in the tree actions
and `spring-boot-dashboard.app.local.dashboard` switch to the tab, build it
again from the terminal of the running app when the tab was closed, and
restore the layout: a pane you closed comes back and the sizes are reset.
Entering the tab restores a missing pane too. When the app stops, by Stop or
by itself, coc wipes its terminal. With `spring.dashboard.layout.cleanup`
"always" (the default) the tab closes with it, in one `:tabclose`; the last
tab of Vim stays open. With "keep" the tab stays with the views and the next
run fills it again.

A coc tree view lives in one window at a time, so the four views are shown in
the app tab you are in: they move there when you enter it, and the other app
tabs keep the terminal only until they are entered. Closing an app tab, by the
dashboard or by hand, keeps the views: the next app tab shows them. The views
show every live app, as they do elsewhere. A view with nothing to show has one
hint row, for example "Run <app> to see its properties" or "No beans yet", or
"Spring Boot server not running" while that server is not up. SPRING APPS
stays its own view on the right of the tab you are in, to start apps from;
browsing the views never opens an app tab.

Going to a bean or an endpoint, the lists of the relations, and the line where
nvim-dap stops in a debugged app, open in the source window of the app: the
window Run, Debug or Attach was started from, while it holds a file, otherwise
the first window of its tab that does. The window and its tab are remembered
by their ids, so moving tabs does not matter. A window takes a source when it
holds a file (no terminal, tree or list), is not a float and is not fixed to
its buffer ('winfixbuf'). When there is none, the tab is closed, or there is
no app (a tree outside an app tab), they open in a float over the current tab,
centered and `spring.dashboard.layout.fallbackSize` percent (default 75) of
the width and height of the screen: the file at the line, the relations in a
location list below it. In Vim the float is a popup that cannot be entered: it
shows the file at the line, or the relations as lines, and closes when the
cursor moves.

Debug starts the JVM suspended, so that breakpoints in the startup code are
hit, builds the app tab, goes back to the source window of the app (see above)
and attaches the debugger from there, so a debugger UI that opens when the
session starts opens in the source tab, not in the app tab. Attach debugger
(`spring-boot-dashboard.app.local.attach`) does the same for an app that Run
started. Debugging needs nvim-dap (Neovim) or vimspector (Vim and Neovim,
Python 3); without them Debug says so, Run still works. A stop of nvim-dap
shows its line in the source window of the app (see above). vimspector opens
its own debug tab and shows its stops there; it needs no .vimspector.json, and
counts as attached until its session is reset. If no debugger attaches within
`spring.dashboard.debug.attachTimeout` seconds the JVM is killed. Ending the
debug session in the debugger only detaches, the app keeps running.

Every launch combines two layers of the same keys: `profiles`, `port`,
`logLevel`, `logPackages`, `debugReport`, `vmArgs`, `programArgs`, `envVars`.
`spring.dashboard.launch.defaults` is the layer under every app, the settings
of the app (the panel, or its entry in `spring.dashboard.launch.settings` by
the name shown in the tree) go on top: >json
    "spring.dashboard.launch.settings": {
        "my-app": {
            "profiles": ["dev"],
            "vmArgs": ["-Xmx512m"],
            "programArgs": ["--server.address=0.0.0.0"],
            "envVars": { "DB_URL": "jdbc:h2:mem:dev" }
        }
    }
<
  `vmArgs`        the defaults, then the app's; an exact duplicate is
                  dropped, otherwise the later option wins in the JVM.
  `programArgs`   the defaults, then the app's; an app argument with the
                  option name of a default (before `=`) replaces it.
  `profiles`      the defaults, then the app's, each once.
  `envVars`       per variable, the app's value wins.
  others          a value the app sets replaces the default, an empty one
                  (or `debugReport` off) keeps it.

An app can add to a default list, not remove an entry from it. Setting a list
in `spring.dashboard.launch.defaults` itself replaces its default list, keep
the live data options below in a `vmArgs` of your own.

The default `vmArgs` are the options the live data needs; the JMX port, the
host and the project name are added per run: >
    -Dcom.sun.management.jmxremote.authenticate=false
    -Dcom.sun.management.jmxremote.ssl=false
    -Dspring.jmx.enabled=true
    -Dspring.application.admin.enabled=true
    -Dmanagement.endpoints.jmx.exposure.include=*
    -Dmanagement.endpoint.env.show-values=ALWAYS
<
The last one lets Spring Boot 3 show the values of the properties, in the
Properties view and in the address Open in browser opens, instead of `******`.
It also shows them to anyone who reaches the JMX port; remove it to keep the
values hidden.

Stop sends SIGTERM, so that Spring shuts down cleanly, and SIGKILL when the
process is still there after `spring.dashboard.stop.gracePeriod` seconds. It
also stops a local app started outside the dashboard when its live data is
connected, by the pid of that live data. The live data of a dashboard app is
paired by pid, of other apps by their main class.

Attach debugger attaches the debugger to an app Run started, without a
restart; breakpoints hit from then on. The commands:

  `spring-boot-dashboard.app.local.run`
  `spring-boot-dashboard.app.local.debug`
  `spring-boot-dashboard.app.local.settings`
  `spring-boot-dashboard.app.local.dashboard`
  `spring-boot-dashboard.app.local.attach`
  `spring-boot-dashboard.app.local.stop`

Without a tree line they ask which app to use.

`spring-boot-dashboard.app.local.open` opens an app in the browser; it needs
the live data of the app. |coc-spring-dashboard-browser|

PROPERTIES                                   *coc-spring-dashboard-properties*

One line per running app (`●`), with its property sources (`▤`) under it and

------------------------------------------------------------------------------
MEMORY                                           *coc-spring-dashboard-memory*

One line per running app, with three lines under it:

  `heap`        used heap in MB, followed by `/ <max> MB`
  `non-heap`    used non-heap memory in MB
  `gc pauses`   total time of the garbage collection pauses in ms,
              followed by `(count <n>)`

Each line shows a sparkline of the latest values, drawn with `▁▂▃▄▅▆▇█`,
and the current value. Every
`spring.dashboard.memory-view.fetch-data.delay-in-milliseconds` the dashboard
asks the Spring Boot server to fetch the memory and the gc pauses of each
app; a line gets its new value when the server announces that the fetch is
done, so the first values show after the first fetch. The sparkline keeps
`spring.dashboard.memory-view.display-data.max-datapoints` values.

When an app stops its lines disappear.

TREE ACTIONS                                    *coc-spring-dashboard-actions*

Press the actions key of the tree (`<Tab>` by default) on a line to get a
menu of what you can do with it:

  Line             Actions ~
  app              the actions that fit its state, see below
  bean             Go to definition (beans with source), Show
                   dependencies, Show injected into, Show hierarchy
  mapping          Go to definition (mappings with source), Open in
                   browser (running apps only)
  bean or mapping  Show all, Show defined
  group

The actions of an app follow its state in SPRING APPS:

  State                         Actions ~
  `○` stopped                     Run, Run with profile, Debug, Debug with
                                profile, Launch settings...
  `◐` starting, waiting           Launch settings..., Show app dashboard,
                                Stop
  `●` running, started with Run   Launch settings..., Show app dashboard,
                                Stop, Attach debugger, Open in browser
  `●` running, started elsewhere  Launch settings..., Stop, Open in browser
  `◉` debugging                   Launch settings..., Show app dashboard,
                                Stop, Open in browser
  `◎` attached                    none: the app runs elsewhere

Open in browser shows only once the live data of the app is connected.
Launch settings apply to the next start.

SHOW ALL AND SHOW DEFINED                       *coc-spring-dashboard-defined*

A running app has many beans and mappings that come from Spring itself.
Show defined lists only the ones defined in your source, Show all lists
every one. The choice applies to all live groups of the tree and the group
description changes to `live, defined` or `live, all`. Static groups always
show the defined ones.

  `spring.dashboard.bean.showAll`         all live beans
  `spring.dashboard.bean.showDefined`     only the defined beans
  `spring.dashboard.mapping.showAll`      all live mappings
  `spring.dashboard.mapping.showDefined`  only the defined mappings

------------------------------------------------------------------------------
FIND                                               *coc-spring-dashboard-find*

The beans, mappings and properties trees have a filter: press the filter key
of the tree (`f` by default) in the tree, type to narrow the lines, `<Esc>`
ends the filter.

------------------------------------------------------------------------------
BEAN RELATIONS                                *coc-spring-dashboard-relations*

The relations of a bean open in a |location-list| at the bottom:

- Show dependencies, titled "Dependencies of <bean>": the beans it needs,
  as `name: type` for a bean with source.
- Show injected into, titled "<bean> is injected into": the beans that get
  it injected, as `bean <- field` for a bean with source.
- Show hierarchy, titled "Hierarchy of <bean>": its type, then its
  supertypes indented.

For a bean with source the entries come from the source and `<CR>` on an
entry jumps to it. For a live bean without source they come from the
running app.

SIGNS IN THE CODE                                 *coc-spring-dashboard-signs*

Java buffers get a sign in the sign column:

  `◆`   a bean definition
  `↗`   a request mapping

Set `spring.dashboard.enableGutter` to `"off"` to hide them.

==============================================================================
REMOTE APPS                                      *coc-spring-dashboard-remote*

`boot-java.remote-apps` is coc-springboot's list of remote apps reached over
JMX, set in `coc-settings.json` (see |coc-springboot-remote-apps|): >json
    "boot-java.remote-apps": [
        {
            "host": "staging",
            "jmxurl": "service:jmx:rmi:///jndi/rmi://staging:9111/jmxrmi"
        }
    ]
<
  `spring-boot-dashboard.app.remote.connect`
      pick an entry of that list that is not connected and connect it
  `spring-boot-dashboard.app.remote.disconnect`
      pick a remote app the dashboard connected and disconnect it: an
      entry of that list or an app connected by
      |coc-spring-dashboard-attach|

Connect serves only the entries of that list: there is no discovery and no
debugger. Disconnect never offers a local app: its live data follows its own
start and stop (Stop, `spring-boot-dashboard.app.local.stop`). The pick shows
each app by its `host`, with its `jmxurl` beside it. A connected remote app
shows live data in the trees like a local app. coc-springboot's
`springboot.app.connect` offers the entries of the list as well.

To connect and debug an app by its address instead, see
|coc-spring-dashboard-attach|. Local apps started with Run or Debug connect
by themselves.

==============================================================================
ATTACH TO A REMOTE APP                           *coc-spring-dashboard-attach*

`spring-boot-dashboard.app.remote.attach` attaches to a remote app by its
address: an app the dashboard did not start, on another machine, in a
container, behind a forwarded port, or a JVM you started yourself on this
machine. It connects the live data over JMX and attaches the debugger over
JDWP; leave a port empty to skip that half. It opens the app dashboard tab
with the four views first, then attaches. With a debug port it goes back to
the source window before the debugger attaches, as Debug does; with only a JMX
port it stays in the app tab. There is no terminal in that tab. A panel asks
what to attach to: >
     Attach to a remote app
     ▶ Attach with these settings
       Host            localhost
       JMX port        9010  (live data; empty: skip)
       Debug port      5005  (debugger; empty: skip)
       Project         orders-service
       Copy app startup options
<
A row opens a one-line input, Project a pick of the Java projects of the
workspace (an input while there are none), and returns to the panel. Picking
the first line attaches, Esc cancels. With one Java project the Project row
is filled with it. The panel saves nothing: an attach remembers the host and
the ports per project (kept per workspace), also one started with the
command arguments. Picking a project shows its values.

Like the launch settings, two layers of the same keys:
`spring.dashboard.attach.defaults` is the layer under every project, the
values of the project (remembered, or its entry in
`spring.dashboard.attach.settings`) go on top. A key the project sets replaces
the default, an empty port too. An attach remembers the host and the ports
only; the JVM options always come from the settings. Once an attach
remembered them, the host and ports of the settings are no longer used for
that project; change them in the panel or with the command arguments.
Setting `jmxVmArgs` or `debugVmArgs` in `spring.dashboard.attach.defaults`
replaces the default list, keep the live data options in it.

  `host`          localhost by default.
  `jmxPort`       9010 by default, the live data half.
  `debugPort`     5005 by default, the debugger half.
  `jmxVmArgs`     the JVM options Copy app startup options gives for the live
                  data half.
  `debugVmArgs`   the same for the debugger half.

`${host}`, `${jmxPort}` and `${debugPort}` in the options are the values of
the panel. For example: >json
    "spring.dashboard.attach.settings": {
        "orders-service": { "host": "10.0.0.5", "debugPort": "" }
    }
<

Copy app startup options puts the JVM options that match the panel on the
clipboard (register `+`) and the unnamed register, on one line separated by
spaces, and says "App startup options copied". Start the app with them. The
options are the `debugVmArgs`, then the `jmxVmArgs` of the attach settings of
the project, with the values of the panel filled in; the half whose port is
empty is left out. With the default settings, one per line here: >
    -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005
    -Dcom.sun.management.jmxremote.port=9010
    -Dcom.sun.management.jmxremote.rmi.port=9010
    -Djava.rmi.server.hostname=localhost
    -Dcom.sun.management.jmxremote.authenticate=false
    -Dcom.sun.management.jmxremote.ssl=false
    -Dspring.jmx.enabled=true
    -Dspring.application.admin.enabled=true
    -Dmanagement.endpoints.jmx.exposure.include=*
    -Dmanagement.endpoint.env.show-values=ALWAYS
<
After the JMX port options, the default `jmxVmArgs` are the options the live
data needs, the same as the default `vmArgs` of the launch settings.
|coc-spring-dashboard-apps|

The live half needs the Spring Boot server, the debug half a debugger
(nvim-dap or vimspector) and the Java server. A missing one is named and the
other half still runs. A half that fails does not undo the other.
`spring-boot-dashboard.app.remote.disconnect` disconnects its live data
again.

The command takes optional arguments, which skip the panel: host, JMX port,
debug port and project. Without a project the only Java project of the
workspace is used; with several, name the project. A missing host or port is
the value of the project (remembered, or from the settings), an empty string
skips that half: >
    :CocCommand spring-boot-dashboard.app.remote.attach localhost 9010 5005 orders
<
Not to be mixed up with `spring-boot-dashboard.app.local.attach`, which only
attaches the debugger to a local app started with Run, at the port Run opened.

==============================================================================
OPEN IN BROWSER                                 *coc-spring-dashboard-browser*

Open in browser on an app opens its root url, on a mapping it opens the url
of the endpoint. The url follows `spring.dashboard.openUrl`, filled in with
the port and context path the live data of the app reports, so both need
its live data. A context path Spring hides as `******` counts as none.

==============================================================================
MESSAGES                                       *coc-spring-dashboard-messages*

"Java server starting"
    Run, Debug, Attach debugger, Launch settings and the refresh of the apps
    need the Java server (coc-java), up and done importing the projects. Wait
    until it has imported them.

"Spring Boot server not running"
    The live data refresh and the remote apps need the Spring Boot server
    (coc-springboot). The empty views say the same.

"... not active"
    coc-springboot or coc-java is not installed or did not start. Install
    them, open a Java file of the project and restart coc with `:CocRestart`.

"Dashboard not started", "Apps not resolved",
"Beans and endpoints not loaded", "Live data not refreshed",
"... did not start", "... not stopped"
    The step failed. The reason is in the output channel:
    `:CocCommand workspace.showOutput Spring Dashboard`.

"No debugger found"
    Debug and Attach debugger need nvim-dap in Neovim, or vimspector.
    Install one, or use Run.

"Debugger not attached", "... stopped, no debugger"
    The debugger did not attach in `spring.dashboard.debug.attachTimeout`
    seconds, a debugged app was stopped. Raise the setting.

"... already running", "... not running"
    Run and Debug need a stopped app, Stop a running one.

"... is attached as a remote app"
    The app runs elsewhere and is connected with Attach to a remote app.
    Disconnect it (`spring-boot-dashboard.app.remote.disconnect`) to Run or
    Debug it here.

"... not started with Run"
    Attach debugger works on an app that Run started.

"... app not running"
    Open in browser on a mapping needs the app to run.

"... not connected"
    Open in browser needs the live data of the app, which connects a few
    seconds after the start.

"No remote app configured", "No remote app to connect",
"No remote app connected"
    `boot-java.remote-apps` is empty, all its apps are connected, or none
    of them is connected. |coc-spring-dashboard-remote|

"No Spring Boot app found"
    The Java server found no class with `@SpringBootApplication` in the
    workspace. Open a Java file of the project and wait until the Java
    server has imported it, then try again.

"Every app is running", "No app is running", "No app dashboard"
    Nothing to pick for the command: Run and Debug need a stopped app, Stop
    and Open a running one, Attach debugger one Run started, Show app
    dashboard one that has run.

"No connected app"
    `spring-boot-dashboard.livedata.refresh` has no connected app to refresh.

"... live data connecting", "... debugger attached"
    The two halves of Attach to a remote app, each says how it went.

"Nothing on host:port", "No port to attach", "No project to attach"
    Attach to a remote app found nothing listening on the debug port, both
    ports are empty, or no project was picked. |coc-spring-dashboard-attach|

"Stopping ...", "Found ... apps", "Refreshed ... apps", "Connecting ...",
"Disconnected ..."
    A short notice for a change that is not on screen.
